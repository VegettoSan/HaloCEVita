# Original Main Menu path (source inspection, 2026-09-29)

This is a source-level call graph, not a claim that the entire path has run on Vita. `ui.map` metadata/accessors ran on hardware in 00.07; 00.08 hardware confirms the persistent mount and original `ui_widgets_initialize`. The 00.08 heap dump shows the 16 KiB widget pool remained allocated at exit; 00.09 hardware confirms it is freed before both unmounts. 00.11 hardware confirms the original root and both creation handlers; update/render remain unentered.

## Startup and cache lifetime

1. `main_loop` calls `game_initialize` (`source/main/main.c`, `source/game/game.c`). `game_initialize` calls `ui_widgets_initialize`, which allocates the 16 KiB widget pool, resets it and initializes `widget_globals` (`source/interface/ui_widget.c`).
2. `main_loop` dispatches `main_menu_load` when `want_to_be_at_main_menu` is set. `main_menu_load` calls `main_load_ui_scenario(FALSE)` if needed, then `main_screen_shell_load`, `main_menu_precache_resources`, and the time/script/update-server new-map functions (`source/main/main.c`).
3. `main_load_ui_scenario` precaches `levels\\ui\\ui`, creates `game_options`, disposes the previous map, and calls `main_new_map`. The latter calls `game_load` -> `scenario_load` -> `scenario_tags_load` (`source/main/main.c`, `source/game/game.c`, `source/scenario/scenario.c`, `source/cache/cache_files.c`).
4. `scenario_tags_load` opens the UI cache, reads its tag section into the physical tag-cache region, registers the tag directory and vertex/index buffer directories, and leaves `tags_loaded` set. `scenario_load` obtains the scenario definition, loads `globals\\globals`, and switches to BSP 0. `game_initialize_for_new_map` then initializes rasterizer, game state, interface and other new-map systems. The existing Vita tag reader/mount supplies only the validated UI tag image; it does not yet implement this full scenario/BSP/resource contract.
5. `main_load_ui_scenario` calls `main_menu_active(TRUE)` only after `main_new_map` returns. `main_screen_shell_load` then calls `ui_widget_load_by_name_or_tag("ui\\shell\\main_menu\\main_menu", ...)`. That function obtains the original DeLa tag, allocates a `widget_instance`, initializes children recursively, and dispatches creation event handlers. It also may initiate filesystem checks, intro playback, audio, and virtual keyboard initialization. These branches need real platform/game contracts before activation on Vita. Host metadata inspection of the user-owned `ui.map` shows the root has event type 24/function index 23: `_widget_event_created` -> original `main_menu_initialize` in `ui_widget_event_handler_functions.c`. That handler clears player UI joins/variant, disposes network client/server, disables remote connections, resets spawn count, ends profile editing and starts menu music. The game-demos child also has a creation handler (type 24/function 86). This is a real runtime dependency, not an optional future menu action.

The source and user-owned `ui.map` show the precise first creation-event order. `widget_instance_initialize` recurses through children before the root's event. The game-demos child has event type 24/function 86/flags 0x80, calling original `disable_widget_if_no_xdemos` -> `xbox_demos_available` -> `file_reference_create_from_path`/`file_exists` on `d:\\XDemos\\XDemos.xbe`. The root then has event type 24/function 23/flags 0x80, calling `main_menu_initialize` and its player UI/network/audio state. Its `ring_loop` script text does not execute because the script flag is clear. Both event handlers are real runtime requirements before the first menu frame.

## Update and render

1. Each `main_loop` frame calls `process_ui_widgets`. It handles initialization-thread completion, controller/events, focus, child processing and timers (`source/interface/ui_widget.c`).
2. The active game frame enters `main_game_render` -> `render_frame` -> a player/nonplayer render window. `render_frame_pregame` also invokes `render_ui_widgets` in the pregame path (`source/main/main.c`, `source/render/render.c`). The exact first render window used by the retail UI has not been observed on Vita.
3. `render_ui_widgets` walks `widget_globals.active_widgets` and calls `widget_instance_render_recursive`. The latter resolves the original DeLa definition, game-data inputs, background bitmap, text/list content and children (`source/interface/ui_widget.c`). Bitmap, Unicode string and font accessors are proven on 00.07 hardware; pixels and widget instances are not.
4. For a bitmap background, `widget_instance_render_recursive` calls `draw_bitmap_in_rect` -> `rasterizer_psuedo_dynamic_screen_quad_draw` -> `_rasterizer_psuedo_dynamic_screen_quad_draw` (`source/interface/ui_widget.c`, `source/rasterizer/rasterizer.c`, `source/rasterizer/xbox/rasterizer_xbox_dynavobgeom.c`). The last function applies D3D render/texture state, `rasterizer_set_pixel_shader`, screen-geometry vertex shader permutation 4/type 8/permutation 1, then `IDirect3DDevice8_Begin(D3DPT_TRIANGLEFAN)`, four original screen vertices and `IDirect3DDevice8_End`. This is a source-derived candidate for a menu bitmap's draw, not an observed first draw.
5. The XDK inline `IDirect3DDevice8_End` reaches upstream `D3DDevice_End` in `port/linux/src/d3d8_gl.c`: `prepare_draw(TRUE)` builds/binds the NV2A-translated program and state, then uploads the immediate vertices and calls `glDrawArrays` for the triangle fan. The original `d3d8_resources.c`/`xbox_textures.c` supply resources. `render_frame_present` -> `rasterizer_present` submits the frame. Full backend linkage and retail resource registration are still absent on Vita.

## Current integration boundary

00.08 keeps the validated `ui.map` image mounted and calls the original `ui_widgets_initialize`; both are hardware-confirmed. 00.09 hardware confirms checked teardown for this state with no widget instances. 00.10 hardware confirms a separate pre-root call through original `file_reference_create_from_path`, `file_exists`, and `xbox_demos_available` for the first child event's file dependency. It deliberately does not call `ui_widget_load_by_name_or_tag` yet: after the file check, the root enters `main_menu_initialize` with player UI, network and audio state. The common widget/event closure also depends on game time, script evaluation, audio, player control and update-server/new-map functions. A link experiment forcing only this root entry point yielded 17 unresolved references across 11 distinct original functions, recorded in `build/vita/logs/menu-root-link-probe.txt`. The original event dispatcher stores 102 function pointers in one table, so linking it retains a broad game/menu dependency graph. Supplying success stubs would make the widget state untrustworthy. The map/BSP/resource and renderer contracts above remain required before a draw can be claimed.

## 00.11 UI bring-up checkpoint

The user-owned `ui.map` graph contains nine widgets when the column-list extended description is included. Its function indices are exactly 0, 23, 86, 87 and 101. Only 86 (game-demos child) and 23 (root) have creation events; both specify just run-function flag 0x80. No widget requests game-time pause. Under Vita the dispatcher selects those original functions by index, leaving the 102-entry function-pointer table unchanged elsewhere and failing explicitly on unsupported interactive indices. This allows dead-code elimination of unentered handlers. The original `main_screen_shell_load` argument tuple is used unchanged.

00.11 fast startup calls original player UI initialization and root creation after persistent mount; 025 begins the call, 026/027 trace the original child/root handlers, and 028 requires the returned active root and 9/3 graph. A031 real Vita logs all of these through 028: root `0x81707e9c`, nine widgets, three direct children, focused widget `0x81707f8c`. Music lookup is original but playback is deferred because full game sound state is absent. Active widgets retain their tag cache/arena until process exit. Separately forced `process_ui_widgets` and `render_ui_widgets` links reveal 48 and 34 distinct unresolved dependencies respectively, so these functions and the original D3D8 draw are not entered in the delivered VPK. The BSP/ring is outside this UI-only checkpoint. The static vitaGL logo is expected until original render and present are connected.

Host inspection of the same nine definitions identifies the first background bitmap as the original Halo logo datum `e2870111`; the select-list and build-number widgets invoke original game-data input functions 21 (`main_menu_animation_fakery`) and 8 (`set_textbox_to_build_number`).
