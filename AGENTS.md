## Current verified bring-up baseline

The most recent locally verified Vita state may be newer than the public GitHub status. Treat the following as the minimum known-good bring-up baseline unless the local tree/logs prove a later state:

- VitaGL initialization works on PS Vita.
- Runtime shader compilation has been exercised successfully.
- A visible diagnostic/test triangle has been rendered on screen.
- Real Halo Xbox v5 map files can be opened.
- Tags from real maps, including `ui.map` and `a10.map`, have been read correctly.
- The real Halo Main Menu is **not working yet**.

Do not regress or re-prove these milestones unless a changed subsystem specifically requires regression testing.

## Immediate objective

The next milestone is not another synthetic renderer demo. The objective is to:

1. complete the real initialization path required by `ui.map`;
2. enter Halo's actual Main Menu state;
3. reach the first draw call generated by the original Halo renderer;
4. render that draw through the adapted original D3D8/NV2A -> GL path on vitaGL;

## Porting strategy

- Vita is a native 32-bit ARM target. Prefer a direct `arm-vita-eabi` build.
- Preserve the game's 32-bit pointer/layout assumptions.
- Do **not** copy the Android arm64 ILP32 host/guest loader unless a Vita-specific blocker genuinely requires it.
- Use the Linux native port as the primary platform-layer reference.
- Use the Android port as the primary reference for ARM issues, GLES-oriented renderer fallbacks and ABI fixes.
- Preserve upstream separation: Vita-specific code belongs under `port/vita/` or guarded by a clear `HALO_VITA` path.
- Avoid invasive edits to shared game code. If shared edits are required, explain why in `docs/DECISIONS.md`.

## Main-loop integration research priorities

Before inventing new engine behavior, investigate whether the original Halo contracts can be preserved on Vita. Implement only after the approach is validated against the current source and VitaSDK.

### 1. Relocatable Xbox-style memory arena

Investigate whether Halo's Xbox memory layout can be preserved as **offsets inside one dynamically allocated Vita arena**, instead of requiring the Vita process to map memory at the original absolute Xbox virtual addresses.

The preferred experiment is:

- allocate one bounded arena using VitaSDK memory APIs;
- preserve the original 32-bit Xbox subregion offsets inside that arena;
- make `XPhysicalAlloc` honor requested Xbox-style offsets/alignment where feasible;
- keep Game State, Tag Cache, texture cache and sound cache relationships explicit;
- measure actual Vita memory cost before committing to a large arena size;
- add runtime assertions proving that every returned region is inside the arena and correctly aligned.

Do not assume that a 128 MiB arena is automatically viable. Prove allocation success and remaining user/CDRAM/phycont budgets on hardware.

### 2. Pointer/address translation

Map/cache data may contain Xbox-era addresses. Prefer **typed, structure-aware rebasing or explicit address translation** for known pointers and resource fields.

Do not blindly rewrite every aligned 32-bit value that happens to fall inside an Xbox address range unless there is strong evidence that the specific data region is a relocatable linked-memory image and the transformation has validation safeguards. Arbitrary word scanning can corrupt non-pointer data.

Every new rebase rule must log what it changed and must have bounds checks against the target arena/cache region.

### 3. XAPI / Win32 compatibility required by real startup

Implement the smallest correct native Vita compatibility layer needed by Halo's real startup path. Investigate and add semantics incrementally for functions such as:

- file open/read/write/seek/size and file attributes;
- case-insensitive Xbox path translation and directory enumeration;
- overlapped/alertable file completion behavior where Halo actually relies on it;
- events and mutexes;
- thread creation, suspended start/resume, wait and exit status;
- per-thread `GetLastError` / `SetLastError` behavior;
- high-resolution timing and `FILETIME` conversions;
- Xbox controller discovery/state calls required by the Main Menu path.

Do not add broad fake success stubs merely to eliminate linker errors. A function that affects startup correctness must either implement the required semantics or fail loudly and be recorded as a blocker.

### 4. Contract tests before engine dependence

For each platform primitive above, create small contract tests that run on real Vita hardware before relying on that primitive inside the full Halo main loop.

Useful tests include:

- exact Xbox-style map path opens `ui.map`;
- directory enumeration does not return unrelated entries;
- seek + overwrite preserves expected file position;
- overlapped callbacks execute on the expected issuing thread when alertable waits are used;
- auto-reset/manual-reset events behave correctly;
- recursive mutex behavior matches the caller's expectations;
- suspended threads do not execute before resume;
- thread result and per-thread last-error values are preserved;
- controller axes/buttons match the XInput ABI and original Halo dead-zone path.

A successful link is not proof that these contracts work.

## Graphics strategy

Preferred route:

`Xbox D3D8/NV2A state -> upstream d3d8_gl/nv2a shader translation -> Vita-compatible GL subset -> vitaGL -> SceGxm`

- Reuse upstream shader translators (`nv2a_vsh.c`, `nv2a_psh.c`) where possible.
- Preserve the original `d3d8_gl.c`/resource architecture rather than replacing it with a simplified D3D8 facade.
- Prefer adapting generated GLSL to vitaGL's supported translator subset over rewriting the entire Halo shader system.
- Use `libshacccg.suprx`/VitaShaRK when required by vitaGL runtime shader compilation.
- Treat unsupported GL calls one by one. Add wrappers/fallbacks and document them in `docs/GRAPHICS_COMPATIBILITY.md`.
- Treat `docs/VITAGL_RENDERER_PLAN.md` as the renderer/shader implementation roadmap; update it when hardware evidence changes a capability, fallback or implementation order.
- Treat `docs/VITA_RENDERER_BEHAVIOR_CONTRACTS.md` as the regression guard for UI coordinate space, primitive topology, resource/raster ordering, alpha semantics and GL state invalidation. Do not rescale retail widget data, force UI alpha opaque, or replace the vitaGL backend merely to mask a renderer-state defect.
- Do not silently stub a rendering function if it affects correctness. A temporary stub must log itself and be recorded as a known issue.
- In particular, do not return fake-success shader handles or ignore `SetVertexShader`, shader constants, pixel shader programs, render targets, vertex declarations, or texture state merely to reach a frame. The first real Halo draw is only meaningful if the relevant NV2A/D3D state reaches the translated shader/render path.
- A visible triangle proves the VitaGL/shader path, not the Halo renderer. Keep this distinction explicit in status reports.

## ABI rules for ARM32

- Preserve 32-bit pointers/longs and Xbox/MSVC layout assumptions.
- Keep Xbox/Halo `wchar_t` behavior distinct from VitaSDK/newlib wide-character ABI where required.
- Keep Halo enums 32-bit where layouts or API contracts depend on them.
- Treat variadic functions and float-containing prototypes as high risk on ARM hard-float.
- Do not hide incompatible function-pointer, implicit-declaration, return-type, or pointer-conversion problems merely to obtain object files. Investigate and correct the contract when those diagnostics can change ARM calling convention or data layout.
- Successful compilation of every translation unit is not proof that cross-unit ABI contracts are correct.

## Memory and performance

- Do not carry Android buffer sizes into Vita blindly.
- Keep memory budgets explicit. Vita has limited RAM/VRAM compared with modern Android devices.
- Start with correctness and observability, then optimize.
- Target 30 FPS first, matching the original Xbox design goal. Do not optimize for 60 FPS before a stable 30 FPS path exists.
- Record changes to stream/index buffer sizes and measured consequences.

## Definition of progress

A change is not considered working merely because it compiles. Mark a feature working only when there is reproducible evidence at the appropriate level:

- `COMPILES`: builds successfully;
- `LINKS`: final Vita ELF/VPK links;
- `BOOTS`: launches on Vita/Vita3K far enough to produce expected logs;
- `RENDERS`: visible expected graphics;
- `PLAYABLE`: interaction/gameplay verified;
- `STABLE`: repeated tests without the known failure.

Use these terms consistently in `docs/STATUS.md`.

For graphics, distinguish:

- `DIAGNOSTIC RENDERS`: authored test geometry/shader path works;
- `HALO DRAW REACHED`: original Halo code issued the draw/state sequence;
- `HALO DRAW RENDERS`: that original draw produced the expected visible output.

Do not collapse these into one milestone.
